# 用户认证与权限管理 · 设计说明

> 状态：**P0 已实施**（登录、首登改密、内置角色与职能域种子、页面归属对账、超管唯一自检）。
> 域授权矩阵、审计落库与车间 IP 白名单仍待 P1 落地，本文档仍是后续分期的设计基线。

> P0 落地时与本文档的差异仅一处：车间终端的 `BoardTerminal` claim 已预留但未使用，
> 登录闸门尚未区分只读终端——这是 P1 的范围，不影响当前行为。

## 1. 目标与非目标

### 1.1 目标

1. 引入登录，未认证用户不能访问任何业务页面与接口。**唯一例外**是车间的公用终端（6.6）：按 **IP 白名单**免登录签发只读会话，只能看到钞纸域的查看类页面（即「数据指标」下的全部页面），不能修改任何数据、不能进入平台管理。
2. 按**职能域**控制页面可见性：不同部门看到不同业务板块的页面。
3. 按**角色**在域内再分一层：普通用户只看到查看类页面，技术人员能看到配置类页面并可修改。
4. 「平台管理」仅超级管理员可见可用。
5. 职能域与域内页面可在平台后台维护，不必每次改代码发版。
6. **配置类写操作**留痕（谁、何时、改了哪个对象），查询与登录不留痕。
7. 预留 LDAP / OIDC 对接能力，接第二家 IdP 只加配置不改业务代码。

### 1.2 非目标（本期明确不做）

| 项 | 原因 |
|---|---|
| 行级数据过滤（同页面按部门或班组过滤数据） | 已确认：同域的部门看同一批页面、同一份数据。部门只决定「进不进得来」；班组是数据口径，不是授权单位（见 3.5） |
| 逐页授权（用户 × 页面 勾选矩阵） | 页面只分「查看类 / 配置类」两档，由角色等级决定，不为每个页面建权限点（见 3.3） |
| 级联授权（部门管理员自行扩大本部门域授权） | 存在自我提权风险，域授权只由超管配置 |
| 登录与查询审计 | 只对配置类写操作留痕，见 9.4 |
| 后台创建全新路由的页面 | 页面是 Blazor 组件，配置无法生成。后台维护的是「已有页面归属哪个域」，见第 4 节 |
| 多租户 | 单实例单组织，部门即边界 |
| 车间终端的深色 / 大屏专用主题 | 本期沿用现有设计风格。深色底属于设计体系的新增用途，须先在 `docs/DESIGN_SYSTEM.md` 登记才能使用（6.6） |

## 2. 术语

| 术语 | 含义 | 例子 |
|---|---|---|
| 职能域 BusinessDomain | 业务板块，页面可见性的授予单位 | 钞纸、印钞、能源 |
| 部门 Department | 组织单元，用户的唯一归属；同时也是域授权的授予对象 | A 部门、B 部门 |
| 角色 Role | 操作能力的集合，按用户分配；带一个**页面等级** | 普通用户、技术人员、部门管理员、超级管理员 |
| 页面等级 AccessLevel | 页面自身要求的最低角色等级 | 查看类（1）、配置类（2） |
| 权限点 Permission | 单个可执行动作，`action.*` 编码 | `action.shift.manage` |
| 系统域 SystemDomain | 不参与授权矩阵、固定归超级管理员的域 | 平台管理 |
| 车间终端 Board Terminal | 按 IP 白名单免登录的只读终端，**全场只有一台、所有班组共用** | 车间那台公用电脑（6.6） |
| 只读会话 | IP 命中白名单时签发的会话，只带「域 + 等级 1」，无用户身份、无权限点 | `board@192.168.10.50` |

**关键区分**：域决定**能不能进这个板块**，角色等级决定**板块里能看到哪些页面**，权限点决定**页面里能点哪些按钮**。三层依次收窄。

同样重要的一条：**超管是短路，不参与任何一层计算**——不查域授权、不查页面等级、不查权限点。短路必须是显式分支，而不是"恰好给他配了全部权限"，否则新增一个域就要记得给超管补一次授权。

## 3. 权限模型

### 3.1 四条主线

```
部门 ──授予──> 职能域 ──包含──> 页面            （板块可见，按部门配置）
                                  │
                            页面等级：查看类 / 配置类
                                  │
用户 ──分配──> 角色（页面等级 + 权限点）         （域内可见范围 + 可写范围，按用户配置）
用户 ──属于──> 部门（单值）                      （组织，由目录同步）
配置类写操作 ──> 审计日志                        （留痕，见 9.4）
```

- 一个用户**只属于一个部门**，与 LDAP / AD 的组织模型一致。因此可见域是单值传播，不存在「多部门权限取并集还是交集」的问题。
- 一个部门可被授予**多个域**（A 部门同时可见钞纸与能源）。
- 一个域可授予**多个部门**（能源域给 A、C、G）。
- 同一部门内**不同用户角色不同**——不仅可写范围不同，**可见页面范围也不同**（普通用户看不到配置类页面）。

### 3.2 三层判定

```
可见域(u)   = 部门(u) 被授予的域 ∪ { 系统域 | u 有 super-admin }
可见页面(u) = { p | p.domain ∈ 可见域(u) ∧ p.is_enabled ∧ p.domain.is_enabled
                  ∧ p.access_level ≤ 等级(u) }
可写(u)     = 角色(u) 的权限点并集
```

`super-admin` 短路：等级视为 99，直接返回全部域与全部页面，**不查授权表**。

四条必守规则：

1. **系统域不参与授权矩阵**。`business_domains.is_system = true` 的域在矩阵页面不出现，只由 `super-admin` 角色决定。这样「平台管理只给超管」是显式规则，不依赖「管理员忘了勾」。
2. **页面等级只在域内生效**。等级再高，域没被授权也看不见——技术人员不能因为等级够了就越过部门授权。
3. **域被停用 = 域内页面全部不可见**，但授权记录保留。恢复启用后权限自动回来，不需要重新配。超管也不例外（停用是生命周期状态，不是权限）。
4. **越权访问一律 403**，不是「隐藏菜单但地址可访问」。前端隐藏只是体验，判定在服务端。

### 3.3 为什么不采用逐页授权

页面只分两档（查看 / 配置），不做「用户 × 页面」勾选矩阵。两者代价差距很大：

| | 逐页授权 | 页面等级（本方案） |
|---|---|---|
| 配置量 | 部门数 × 页面数（6 页 × N 个部门），每加一页全表重配 | 两个动作：部门勾域 + 用户选角色 |
| 新增页面 | 必须记得给每个相关部门补勾，漏了页面静默消失 | 代码声明 `AccessLevel`，自动生效 |
| 表达能力 | 可精确到单页 | 只能分两档 |

代价要讲清楚：本方案**无法表达**「某部门只能看历史指标、不能看横向对比」这类细粒度差异。真有这种需求时，正确做法是拆分域或增加角色等级，而不是给每页挂勾选框——逐页授权一旦铺开，配置量与出错概率会随页面数量线性增长，而收益通常只体现在个别人身上。

### 3.4 举例

设 A 部门被授予「钞纸」域，「印钞」「能源」域已创建但尚未挂载页面。钞纸域共 6 个页面：查看类 4 个（能耗仪表板、历史指标、班组横向对比、班组能耗报表），配置类 2 个（排班时间管理、排班日历）。

| 用户 | 部门 | 角色 | 顶栏可见 | 可见页面 | 可执行写操作 | 登录落地页 |
|---|---|---|---|---|---|---|
| 张三 | A | 普通用户 | 钞纸 | 4 个查看类 | 无 | 能耗仪表板 |
| 李四 | A | 技术人员 | 钞纸 | 全部 6 个 | 排班导入与修改 | 能耗仪表板 |
| 王五 | C | 普通用户 | 无（印钞是空域，5.2 默认不展示） | 0 个 | 无 | `/coming-soon` |
| 赵六 | A | 超级管理员 | 钞纸 + 印钞 + 能源 + 平台管理 | 全部 | 全部 | 平台概览 |

张三**不是全站只读**：他连排班页都看不到，左侧菜单只有 4 项。李四能看到钞纸域全部 6 页，其中只有排班页的按钮可点。二人同部门、同域，差别同时体现在「看到几页」和「能改哪页」两处——这是三层收窄的结果：域相同，页面等级不同（1 vs 2），权限点不同（无 vs `action.shift.manage`）。

王五这一行是容易被忽略的边界：C 部门确实被授予了印钞域，但域内没有页面，所以顶栏看不到、也进不去，落地页是「已授权但未上线」而不是「无权限」。

### 3.5 边界：班组是业务维度，不是组织单元

平台现有的六个页面全部以**班组**为数据口径，而外部目录提供的是**员工 → 部门**。两者是不同的维度，不能合并，也不需要合并：

| | 身份维度 | 业务维度 |
|---|---|---|
| 数据来源 | LDAP / OIDC（员工、部门） | 平台自有（班组、排班、能耗） |
| 回答的问题 | 这个人能不能进 | 数据按什么口径聚合 |
| 参与鉴权 | 是 | **否** |
| 变更频率 | 入转调离 | 每个排班周期 |

当前代码已是这个形态，三处佐证：

- `ShiftScheduleRowDto` 只有 `TeamCode` / `TeamName`，排班 Excel 只要求「自然日 / 班组名称 / 上班时间 / 下班时间」四列，**不含姓名与工号**；
- 能耗指标以 `teamCode` 为唯一分组键，没有任何用户维度；
- 仪表板的默认班组由 `ResolveCurrentTeam` 按**当前时间 + 当天排班行**推算，**与登录人无关**。

所以「人来自目录、数据按班组」本身是自洽的。真正要防的是把两者混成一张表。

**硬规则：授权数据只允许引用 `department` / `role` / `domain`，禁止引用 `team_code`。**

**配套规则：登录主体只能是员工个人，不得为班组设共享账号。** 班组不是能承担责任的主体，一旦共享账号，审计只能记到「某班组」，等于没记。班组那台公用电脑按 IP 白名单免登录（6.6），技术人员等个人终端则各用各的账号——两种形态并存，不需要谁代表全组。

四条理由：

1. **目录不提供班组，同步不出来。** 只能手工维护，漏配的表现是「登录后菜单少了几项」，不报错、不告警。
2. **班组会轮转。** 四班三运转下人员调班是常态，权限随班次漂移既不可预期也无法审计。
3. **班组可能跨部门。** 若一个班组由多个部门抽人组成，班组授权等于绕过部门边界。
4. **与已确认的「按职能域授权」冲突。** 同一批页面会出现两套准入规则，冲突时无法判定谁优先。

#### 将来可能需要人↔班组关联的三个场景（均不在本期）

| 场景 | 前置条件 |
|---|---|
| 「我的班组」默认筛选 | 可加 `app_users.preferred_team_code`，**只影响默认选中项，仍允许切换到其他班组**。一旦禁止切换，它就变成了隐式数据权限，必须走正式的行级过滤设计（即 1.2 已排除的项） |
| 人级排班（排到具体某个人） | 必须以**工号**为键，**不得按姓名关联**——重名、改名、同音字都会错。排班 Excel 需增列工号，`external_identities` 需存 `employee_no` |
| 班组归属某部门（「A 部门有哪些班组」） | 需要显式的 `teams.department_id` 映射，由平台维护；**不可由部门名或排班表推导**——「A 部门含甲乙丙丁」并不必然成立 |

一条低成本的前置：**即使本期不做人级排班，也建议在 `external_identities` 里存下 `employee_no`**。LDAP 的 `employeeID` 与 OIDC 的自定义 claim 都能提供，成本几乎为零，而它将来是人级数据唯一的可靠关联键。

## 4. 域与页面的配置方式

需求是「职能域以及对应的页面需要在平台进行设置」。但页面本身是 Blazor 组件，无法由表单生成。所以采用**代码声明 + 平台覆盖**：

| 项 | 来源 | 平台可改 |
|---|---|---|
| 路由 `/energy-dashboard` | 代码 `@page` | 否 |
| 页面标识键 | 代码 `NavItem.PageKey`（稳定不变） | 否 |
| 默认所属域 `banknote-paper` | 代码 `NavItem.DomainCode` | **是**（可改挂到其他域） |
| 页面等级 | 代码 `NavItem.AccessLevel`（查看 / 配置） | 是（改档需评估，见下） |
| 显示名称 | 代码默认值 | 是 |
| 所属分组标题 | 代码默认值 | 是 |
| 排序 | 代码默认值 | 是 |
| 启用 | 默认启用 | 是 |
| 域的名称 / 排序 / 启用 / 是否系统域 | 无代码默认 | 是（域本身可新建） |

页面等级虽可改，但它是**安全相关**字段：把「平台概览」误改为查看类，等于对全部登录用户开放该页。因此后台改档需要二次确认，并写入审计（见 9.4）；代码侧仍保留默认值，`override` 行可一键「恢复默认」。

### 4.1 启动对账（reconciler）

应用启动时执行一次 `DomainPageReconciler`：

1. 扫描 `NavigationCatalog` 中声明的全部页面，按 `PageKey` 与 `domain_pages` 表比对；
2. **代码有、库中无** → 插入新行，取代码声明的默认值，标记 `source = 'code'`；
3. **代码有、库中有** → 仅当 `source = 'code'` 时更新默认值；管理员改过的行（`source = 'override'`）不覆盖；
4. **库中有、代码无** → 标记 `is_orphaned = true`，不删除。后台以「已下线」列出，管理员确认后可删除该记录（**代码里仍存在的页面不允许删除**：删了会在下次启动被对账重建，删除变成一次无效操作，还会让人误以为页面已下线；要隐藏请用停用）。

这一步是整套设计的安全阀。**如果没有对账，把页面归属做成纯数据库配置，新页面部署后不会出现在任何菜单里，且不报错**——这是这类系统最常见的线上故障。

### 4.2 新增页面 / 新增域的流程

| 场景 | 操作 |
|---|---|
| 开发新页面（已有域内） | 代码加 `@page` + `NavigationCatalog` 登记，部署后自动入库并归入声明的域，无需后台配置 |
| 开发新域（如印钞） | 后台先建域 `banknote-printing`；页面代码声明 `DomainCode = "banknote-printing"`，部署后自动归入；随后在矩阵里勾选 C/D/E 部门 |
| 调整页面归属 | 后台改页面的「所属域」，该行 `source` 变为 `override`，重启不再被代码覆盖 |
| 临时下线某页面 | 后台停用，无需改代码发版 |
| 域已建但页面未开发 | 见 5.2 空域呈现 |

### 4.3 空配置兜底

「登录后没东西可看」有三种成因，处理方式必须区分——它们的用户心理预期完全不同：

| 情形 | 用户看到 | 处理 |
|---|---|---|
| 域表为空 | 除超管外全员无页面 | 启动日志警告；超管建域并在矩阵授权 |
| 有部门但无任何域授权 | 落 `/no-access` | 启动时检测并在日志输出警告（不阻断启动）；需超管在矩阵勾选 |
| 已授权但域内无页面（如印钞域） | 落 `/coming-soon` | 文案说明「已授权、板块未上线」，**不得出现"无权限"字样** |

超管不受域限制，始终可进平台管理，因此上述三种情形都不会把超管挡在外面。三个落点的判定顺序见 12.2。

**启动时的实现**：`AuthDataInitializer.WarnOnEmptyAuthorizationAsync` 在初始化末尾检查「域表是否为空」与「有部门但没有任何部门获得域授权」两种情形，写中文告警日志（不阻断启动）；授权不完整时输出「N/M 个部门已授权」的信息日志。

### 4.4 管理功能与入口对照

管理能力必须「有页面、进得去、能生效」，三者缺一都等于没做。当前对照如下（实测于 2026-11-03）：

| 管理功能 | 页面 / 入口 | 关键约束 |
|---|---|---|
| 新建域、改名称/排序/启停/空域展示/系统域标记 | 域与页面配置 `/domain-config` → 「新建域」「编辑域」 | 编码小写字母开头、创建后不可改；系统域不参与授权矩阵 |
| 删除域 | 同页 → 「删除域」 | 仅空域且非系统域；有页面时提示先迁走 |
| 页面归属域迁移、显示名、分组标题、域内排序 | 同页 → 页面行「编辑」 | 路由与页面标识键不可改（代码声明） |
| 页面等级、启停、恢复代码默认 | 同页 → 行内下拉与开关、「恢复默认」 | 等级变更二次确认；恢复默认在下次启动对账生效 |
| 清理已下线页面记录 | 同页 → 「已下线」行「删除记录」 | 只允许删除 orphaned 行 |
| 部门新建/编辑、部门 × 域授权矩阵 | 部门与授权 `/department-grants` | 系统域不出现在矩阵；停用部门不可勾选 |
| 用户新建/编辑、启停、角色、重置密码、批量启停、移交超管 | 用户与角色 `/user-management` | 部门管理员受本部门范围与角色上限约束（9.3） |
| 目录同步状态、手工同步、待处理项标记 | 同页 → 「目录同步」区块 | 仅超管；同步不写角色、不自动启用人工停用账号 |
| 审计查询、筛选、详情、CSV 导出 | 系统审计 `/system-audit` | 只读；保留期 180 天 |
| 采集服务器增删改与连通性测试 | 采集服务器配置 `/acquisition-servers`（平台管理 → 采集配置） | 凭据加密落库；有节点引用时不可删除 |
| 点位增删改、采集点状态 | 点位配置 `/collection-points` | 删除有数据引用的点位需确认 |
| 点位数据定义增删改、调试读取、采集入库、历史 | 点位数据管理 `/managed-data-definitions` 与详情页 | 调试与采集写审计 |
| 排班导入、清空、轮转校验 | 排班时间管理 `/shift-schedules` | 8MB / 20000 行上限 |
| 排班日历查看 | 排班日历 `/shift-calendar` | 只读视图 |

**「采集服务器」原先没有菜单入口**：页面与接口都在，但只能手输地址打开，等于管理功能不可达。已登记进「平台管理 → 采集配置」。这类问题的特征是编译、单测、日志全都正常——只有从菜单点一遍才会发现。

## 5. 导航改造（方案甲）

顶栏由「功能模块」改为「职能域」，域内保留功能分组。

```
顶栏：钞纸 | 印钞 | 能源 | 平台管理
  ├ 钞纸（业务域，可授予部门）
  │   ├ 数据指标：能耗仪表板 / 历史指标 / 班组横向对比
  │   ├ 数据报表：班组能耗报表
  │   └ 班组管理：排班时间管理 / 排班日历
  ├ 印钞（业务域，暂无页面）
  ├ 能源（业务域，暂无页面）
  └ 平台管理（系统域，仅超管）
      ├ 平台概览 / 服务器状态查询
      ├ 采集配置：点位配置 / 点位数据管理
      └ 接口管理：History API 测试 / MQTT 测试
```

### 5.1 改动要点

| 位置 | 改动 |
|---|---|
| `NavItem` | 新增 `PageKey`（稳定标识）、`DomainCode`（默认域）、`AccessLevel`（查看 / 配置） |
| `NavigationCatalog` | 顶层由 `NavSection`（功能模块）改为按域分组；分组结构下沉一层 |
| `MainLayout` | 顶栏渲染「用户可见域」列表，而非静态三个模块；域列表由服务端返回 |
| `NavMenu` | 只渲染当前域的分组，逻辑基本不变 |
| 路由反查 | 由「按最短前缀找模块」改为「按 `domain_pages.route` 最长前缀找域」 |

**只有一个域有内容时的表现**：非超管用户的顶栏可能只有「钞纸」一项（因为印钞、能源是空域，默认不展示，见 5.2），左侧直接是三个分组。这是预期行为，不是布局缺陷。

### 5.2 空域怎么呈现

「印钞」「能源」两个域在库里已存在，但下面没有任何页面（页面已排期，近期开发测试仍以钞纸为主）。这里有一个取舍：显示出来会让人点进空白页，完全不显示又看不出平台规划了什么。

**建议方案：按角色区别对待。**

| 角色 | 顶栏是否显示空域 | 点进去看到什么 |
|---|---|---|
| 普通用户 / 技术人员 | 否 | —（看不到，也点不到） |
| 部门管理员 | 否 | — |
| 超级管理员 | 是，带「未上线」灰色标记 | 空状态：域名称 + 「该板块尚未接入页面」+ 「前往域与页面配置」按钮 |

理由：

1. **普通用户不该看到空气**。一个点进去什么都没有的板块，比看不到更容易被当成系统故障，且会引发「我的权限是不是没配好」的问询。
2. **超管必须能看到**。域是否创建成功、页面是否挂载正确，需要有地方验证；如果超管也看不到，配置效果无从确认。
3. 标记要显式。顶栏项后缀一个「未上线」灰标，让超管一眼分辨「没有权限」和「没有内容」——这两种情况在界面上极易混淆。

**可选开关**：`business_domains.visible_when_empty`（默认 `false`）。若希望向业务方预告规划，可对特定域打开，此时普通用户也能看到，点进去是「该板块正在建设中」的引导页而不是空白。是否启用由你决定，默认关闭。

**还有一个必须处理的边界**：如果某个部门被授予的**全部域都是空的**（例如刚把 D 部门授给印钞域，但印钞页面还没开发），该部门用户登录后会「顶栏空白、无页面可进」。这种情况不能落到 `/no-access`（它表达的是"没有权限"，而实际是"内容未就绪"），应给一个独立提示页：「你所在的部门已获授权，但对应板块尚未上线，请联系管理员」。落地页计算见 12.2。

## 6. 认证

### 6.1 方式：服务端 Cookie 会话

| 方案 | 结论 | 理由 |
|---|---|---|
| **Cookie + 服务端会话** | 采用 | 同源部署，WASM 请求自动携带；浏览器不存令牌，XSS 拿不到凭据；OIDC 的外部令牌全部留在服务端 |
| JWT + 刷新令牌 | 不采用 | 前端需管理令牌生命周期，攻击面与复杂度都更高；当前没有第三方系统调本平台 API 的需求 |
| OIDC 前端直连（PKCE） | 不采用 | 内部系统且有服务端，多一套令牌链路没有收益 |

配置：`HttpOnly` + `Secure`（非 Development 强制，见下）+ `SameSite=Lax`；滑动过期 8 小时，绝对过期 12 小时；登录失败 5 次锁定 15 分钟；写操作走 JSON（跨站表单无法伪造）。

`Secure` 的处理：`SameAsRequest` 的语义是「请求是 https 才加 Secure」，一旦站点被直接以 http 暴露，Cookie 就会明文过网。因此非 Development 一律强制 `Always`（`Auth:Cookie:RequireHttps` 默认 true）。**代价是纯 HTTP 部署时浏览器不会回传会话 Cookie，表现为「登录成功后又回到登录页」**——所以启动日志会明确提示「请确认前端为 HTTPS 或由反向代理终止 TLS」，而不是让运维去猜。

CSRF 有两层：`SameSite=Lax` 挡住跨站表单 POST；`PlatformSameOriginGuard` 再校验 `Origin`/`Referer` 与本站一致（覆盖 SameSite 被削弱、或将来为嵌 iframe 改成 `None` 的场景）。OIDC 回调是 IdP 用 `form_post` 跨站 POST 回来的，已在豁免名单里。没有 Origin/Referer 的请求（curl、健康检查、将来的服务间调用）放行——真正的 CSRF 一定由浏览器发起，浏览器一定带 Origin。

站点若是多人共用的终端（6.5），规划中的 `Auth:SharedTerminalMode`（空闲 15 分钟自动登出、禁用持久化 Cookie）**尚未实现**：当前只有 6.6 的 IP 白名单只读会话这一条免登录通道。因此「在车间公用电脑上以本人账号登录改数据」目前仍会拿到 8 小时滑动 / 12 小时绝对的普通会话，用完必须手动退出。落地时只需两处：登录端点按该开关决定 `IsPersistent`，前端在主布局挂空闲计时器到点调登出；它只影响该站点的浏览器行为，不改变服务端会话时长——否则个人办公电脑上的人每 15 分钟被踢一次，会被当成故障。

### 6.2 Blazor InteractiveAuto 的具体难点

应用是 `InteractiveAutoRenderMode`，同一页面存在两条路径：

- **SSR / 预渲染**：服务端有 `HttpContext`，Cookie 认证状态直接可用；
- **WASM**：没有 `HttpContext`，必须自己实现 `AuthenticationStateProvider` 调 `/api/auth/me`。

因此需要：

| 组件 | 职责 |
|---|---|
| 服务端 `ServerAuthenticationStateProvider` | SSR 阶段由框架提供 |
| WASM `PlatformAuthenticationStateProvider` | 启动时调 `/api/auth/me`，失败则视为匿名；提供 `NotifyAuthenticationStateChanged` 供登录/登出后刷新 |
| `CascadingAuthenticationState` | 根组件包一层，`AuthorizeView` 才生效 |
| `/api/auth/me` | 返回用户 id、姓名、部门、角色、可见域、可执行权限点——一次返回，前端不再分别查权限 |

### 6.3 登录方式（分期）

| 期 | 方式 | 说明 |
|---|---|---|
| P0 | 本地账号 + 密码 | 仅超管；PBKDF2-HMAC-SHA256，迭代 210000，每账号独立盐 |
| P3 | LDAP / AD | 见 11.1 |
| P4 | OIDC | 见 11.2 |

三条通道在 `PlatformAuthService.SignInAsync` 里按顺序判定：**本地有 `password_hash` → 走本地校验；否则 LDAP 启用 → 走域账号校验；都没有 → 中文提示**。域账号的 `password_hash` 恒为 null（平台绝不保存域账号密码），因此「改密」页对它们返回「域账号的密码由目录统一管理」而不是报错。外部账号未走本地失败计数，本地锁定与 AD 锁定不会互相叠加。

### 6.4 超管种子与唯一性（必须前置）

平台当前无登录，一旦启用会立刻锁死所有人。P0 必须包含：

- 启动时若 `app_users` 无任何 `super-admin`，从配置 `Auth:BootstrapAdmin:UserName` / `Password` 创建；
- 该账号 `must_change_password = true`，首次登录强制改密；
- 若配置缺失则**拒绝启动**并输出明确中文日志，而不是静默跳过（否则首次上线无人能登录）。

**超管全局唯一**，这一点按硬约束实现，不靠约定：

| 位置 | 约束 |
|---|---|
| 用户管理页 | 不提供「设为超管」入口，角色下拉只列 `department-admin` 及以下 |
| 服务层 | 分配 `super-admin` 只允许走「移交超管」这一个方法，同一事务内先降级原账号再升级新账号，不出现中间态 |
| 启动自检 | `super-admin` 数量 ≠ 1 时**拒绝启动**（0 个等于锁死，>1 说明唯一性被绕过） |
| 账号保护 | 超管账号不可删除、不可停用、不可改部门；改密只能由本人操作 |

之所以不在数据库层加唯一索引：`user_roles` 是多对多表，唯一性依赖角色 id，用部分唯一索引需要固化内置角色 id，可移植性差。而所有写路径都收敛在「移交超管」一个方法里，配合启动自检已足够；若后续新增了别的授权入口，再补库级约束。

**只有一个超管的实际影响**：超管休假或离职期间无人能改域授权与用户角色。缓解办法是给 `department-admin` 预留启用开关（9.2），需要时临时启用；不建议为此放宽超管唯一性。

### 6.5 共享终端与车间公用电脑

现场的实际形态是：**车间有一台公用电脑，所有班组共用（3–5 人在场时一起看），只看数据**；技术人员与管理员各配个人电脑。两类终端不能套用同一套登录策略：

| 场景 | 人数 | 登录主体 | 做法 |
|---|---|---|---|
| 个人办公电脑（技术人员、管理员） | 1 | 员工本人 | 正常登录，会话随人 |
| 车间公用电脑（只看数据，**全场仅 1 台，所有班组共用**） | 3–5 | **不登录** | IP 白名单免登录，签发只读会话（6.6） |
| 车间公用电脑上确实要改数据时 | — | 员工本人 | 到自己的电脑操作；若只能在该机操作，则在正常地址登录，空闲 15 分钟登出、不记 Cookie |

三条原则：

1. **登录主体只能是员工，不能是班组。** 班组是数据口径，不是能承担责任的主体，「谁改的」无法落到班组头上。
2. **"只看"的终端不应该要求登录。** 让班组的其中一人登录、其余人共用他的会话，等于伪造审计主体；让每人都登录，交接时就是反复登录，与现场操作不符。这类终端按 6.6 用 IP 白名单免登录，并且**只给到查看类页面**——"免登录"与"只读"必须是同一个决定，不能拆成两件事分别实现。
3. **换班不需要任何账号动作。** 默认班组由当前时间与当天排班推算，16:00 交接后自动切到下一班，**没有人需要重新登录**。

第 3 条正好说明「按班组授权」不可行：权限若跟着班组走，同一个人换班后权限就变了，而他登录的身份没变——这种权限漂移既无法向用户解释，也无法审计。反过来说，只要不做班组级授权，换班就只是一个时间函数，与账号完全无关。

### 6.6 车间终端：IP 白名单免登录

**场景**：车间一台公用电脑，**所有班组共用**，3–5 人同时在现场时就着这块屏幕看数据。它只用来**看**，不做任何配置。这类终端不按「用户登录」处理，改用 **IP 白名单**：客户端地址命中即免登录进入，且只拿到查看类页面。

#### 为什么用 IP 白名单而不是令牌

早先设计过「首次粘贴带 key 的链接、之后靠长效 Cookie」的令牌方案，现改为 IP 白名单。两者的差别是实质性的：

| | 看板令牌（原方案） | **IP 白名单（采用）** |
|---|---|---|
| 首次配置 | 必须到那台机器上粘贴一次带 key 的链接 | 服务端加一条地址，客户端零动作 |
| 能否靠转发链接扩散 | 能——把 URL 发出去即可 | **不能**，入口是网络位置而非 URL |
| 同一地址上的其他机器 | 不受影响 | **同样会拿到只读会话** |
| 吊销粒度 | 换 key，立即全部失效 | 移出白名单并重启，或等会话到期 |
| 换 IP / DHCP 漂移 | 不受影响 | 需要重配 |

车间只有一台、机位固定、只读——这三个前提让 IP 白名单的短板都不成立，而它省掉了「上线那天得有人去车间粘一次链接」这个现场动作。**结论依赖那三个前提，缺一条就要重新评估**：例如将来每组各配一台，白名单就成了一组地址，吊销与追溯都会变难。

#### 实现约束：Blazor 电路里拿不到客户端 IP

这是本方案唯一的硬技术约束，也是最容易做错的地方。应用是 InteractiveAuto，页面一旦进入 `InteractiveServer` 电路，`HttpContext` 就不存在了——**在电路内部实时读客户端 IP 是不可能的**。所以 IP 判定只能发生在 HTTP 请求入口，判完必须落成凭据：

```
请求进入（未携带认证 Cookie）
  → 读 Connection.RemoteIpAddress
  → 命中白名单？
      是 → 签发 dap_board 会话 Cookie：claims = board + domain(banknote-paper) + access_level(1)
           → 之后所有请求与 Blazor 电路一律基于该 Cookie 的 claims 判定
      否 → 正常跳 /login
```

**关键点：IP 只决定「是否签发」，授权判定仍然只认 claims。** 全系统因此只有一条授权路径，不存在"这段代码按 IP 放行、那段按身份放行"的双轨制——双轨制一旦引入，两侧判断迟早不一致，而漏洞通常就出在没人核对的那一侧。

反过来说，任何"在每个接口里现查 IP"的写法在本项目都不成立：电路内的后续调用（含 `ServerPlatformApiClient` 直调领域服务）根本没有 `HttpContext` 可读。

#### 授权边界：复用现有页面等级，不新增机制

只读会话的 claims 只有三个，它天然满足下面这组判定：

| 判定 | 结果 |
|---|---|
| `Domain:banknote-paper` | 通过 |
| `Access:View`（等级 1） | 通过 → 能耗仪表板、历史指标、班组横向对比、班组能耗报表 |
| `Access:Configure`（等级 2） | **拒绝** → 排班时间管理、排班日历 |
| `action.*` 权限点 | 一个都没有 → 所有写操作拒绝 |
| `PlatformAdmin` | 拒绝 → 平台管理不可见 |

也就是说，**「把数据指标改成 IP 白名单」在现有模型里就等价于「钞纸域 + 等级 1」，不需要新增任何权限概念**。数据指标（能耗指标 + 数据报表）恰好全是查看类，业务配置恰好全是配置类，这条分界是现成的——不必为白名单单独维护一份页面清单，也就不存在"新加了一个查看页却忘了加进白名单"这种漏配。

#### 五条硬约束（缺一条就是后门）

1. **白名单必须是单机 `/32`，不写网段。** 本方案不做行级过滤，等级 1 本来就能看到全部四个班组的全部历史；开成 `/24` 等于整个网段的人都拿到这份数据。车间只有一台，就只写这一台。启动时若发现宽于 `/24` 的条目，输出告警日志。
2. **那台机器必须有固定 IP。** 静态地址或 DHCP 保留（按 MAC 绑定）。否则地址一变：轻则终端退回登录页（现场表现为"突然要登录了"），重则这个地址被别人的笔记本拿到，那台笔记本开机即得只读会话。这一条要写进部署清单，不是"建议"。**该机器的地址已确认固定（2026-11-03 现场确认），前置条件满足**；实施时仍需在部署清单里登记具体地址并核对白名单条目与之一致。
3. **不能盲目信任 `X-Forwarded-For`。** 当前应用直接跑 Kestrel，`RemoteIpAddress` 就是真实对端地址，没有伪造空间。**一旦前面加了 nginx 之类的反向代理**，必须配置 `ForwardedHeadersOptions` 且只信任已知代理地址；网上常见的"清空 `KnownProxies` 以支持代理"写法，会让任何人通过伪造请求头拿到只读会话。反过来，加了代理却忘了配转发头，则所有请求的 IP 都变成代理地址——白名单要么失效，要么（更糟）把代理地址加进白名单，导致全员可进。
4. **IP 不是身份，不得用于任何写操作。** 它没有用户、没有部门、没有权限点，审计也无法落到人。若车间那台机器确实需要改数据，回到 6.5 的个人登录。
5. **会话绑定签发时的 IP，且固定有效期不滑动。** claims 里带上签发 IP，HTTP 请求层每次比对，不一致立即拒绝并清除 Cookie——这样的 Cookie 即便被复制到别的机器也用不了。有效期固定 12 小时（覆盖一个班次），**不做滑动续期**：续期会让被盗 Cookie 无限延长，而固定到期后由 IP 重新签发，对现场完全无感。已知边界：Blazor 电路只在建立（WebSocket 升级请求）时校验，电路建立后的帧不再走授权管道。

#### 页面表现：不另做一套布局

不新增 `/board` 路由，车间那台机器直接访问正常地址：

- 顶栏显示「钞纸」，左侧只有那 4 个查看类页面，与普通用户看到的完全一致——**做成两套界面就得维护两份，而且现场看到的和用户描述的对不上**；
- 沿用当前设计风格（浅色、现有色板），本期不做深色大屏主题（见 1.2 非目标）；
- 顶栏加一枚「车间终端 · 只读」标识：在场的人能明白为什么改不了，管理员也能一眼分辨当前是不是免登录会话；
- 默认选中**当前在岗班组**，但**允许手动切换**——既然能浏览，就不该把人锁死在一个班组上，这是与「终端只显示单一班组」做法的关键差别；
- 显示「数据截至 HH:mm」，每 60 秒自动刷新数据，但**不重置手动选择的班组与时间范围**（否则现场刚切到乙班，一分钟就被刷回甲班）。

#### 排班解析：可以给默认值，但不能"猜"

现有 `ResolveCurrentTeam` 在**无匹配排班行时**（当天轮休或排班未导入）会用 `today.DayNumber % teams.Count` 推断一个班组，注释写的是「保证仪表板始终有归属」。这在可切换的页面上只是"有个默认值"，但在车间终端会被当成**在岗事实**——现场没有第二处可以比对，看到什么就信什么。

因此默认值必须走严格版本 `TryResolveOnDutyTeam`：

| 情形 | 表现 |
|---|---|
| 命中当天排班且当前时刻在班次内 | 默认选中该班组，并显示「当前班次 08:00–16:00」 |
| 当天轮休 / 无匹配班次 | **不给默认值**，提示「当前无在岗班组」，仍可手动切换 |
| 排班未导入或已过期 | 提示「排班数据截至 X 月 X 日，请联系排班管理员」，**不给默认值** |

差别正在这里：若终端只显示单一班组，宁可整页空白也不显示数据；本方案允许浏览，所以**不隐藏数据，只拒绝猜测默认值**。用户主动选了班组，看到的就是他要的，不存在"系统替我猜错"。

#### 配置与运维

| 项 | 说明 |
|---|---|
| `Auth:Board:Enabled` | 默认 `false`，启用后才生效 |
| `Auth:Board:IpWhitelist` | CIDR 数组，生产只应有一条 `/32` |
| `Auth:Board:SessionHours` | 会话固定有效期，默认 12 小时（覆盖一个班次，避免跨零点到期） |
| 启动校验 | 启用但白名单为空 → **拒绝启动**；存在 `/0`–`/24` 的宽网段 → 启动日志告警 |
| 吊销 | 移出白名单并重启，或等会话到期（最长 12 小时）。没有"换 key 立刻全部失效"那种即时粒度，单机场景可接受 |
| 日志 | 每次签发写一条应用日志（时间、IP、User-Agent），用于追溯这个免登录入口最近被谁用过 |

**与匿名入口的本质差别**：匿名意味着"这个地址任何人都能看"，白名单意味着"只有这个地址能看"；但真正的分野在授权侧——白名单会话仍然要过三层拦截，而匿名入口没有身份，也就没有拦截可谈。

## 7. 授权拦截

### 7.1 三层拦截

| 层 | 位置 | 作用 | 强度 |
|---|---|---|---|
| 1 导航过滤 | `MainLayout` / `NavMenu` | 不渲染无权的域，以及等级不足的页面 | 体验层，可绕过 |
| 2 路由守卫 | `AuthorizeRouteView` + 页面级等级检查 | 直接输入地址时拦到 `/forbidden` | UI 层，可绕过 |
| 3 服务端校验 | 端点策略 + 领域服务装饰器 | 真正的安全边界 | 强制 |

**车间终端（6.6）的只读会话仍然走这三层，不是旁路。** 它的 claims 只有「钞纸域 + 等级 1」，于是第 1 层不渲染配置类页面、第 2 层直接输入 `/shift-schedules` 被拦、第 3 层端点策略与领域服务装饰器同样拒绝一切写操作。**IP 白名单改变的是「怎么拿到会话」，不是「拿到会话之后能做什么」**——这正是它与匿名入口的本质区别。

### 7.2 必须堵的旁路：服务端直调领域服务

当前代码中 `ServerPlatformApiClient` **直接调用领域服务**，不走 HTTP。这意味着：

> 只在端点上加 `[Authorize]` 是无效的——SSR / 预渲染路径根本不经过端点。

处理方式：在领域服务入口加一层授权装饰器，两条路径共用一个校验点。

```
HTTP 端点 ──┐
            ├──> [AuthorizationDecorator] ──> 领域服务（真实实现）
服务端客户端 ┘
```

装饰器从 `ICurrentUserContext` 取当前用户，按「域是否可见」与「是否具备 action 权限点」判定，不通过抛 `ForbiddenException`，端点层映射为 403，页面层映射为「无权限」中文提示。

### 7.3 动态策略

域可在后台新增，策略名无法在编译期固定。使用 `IAuthorizationPolicyProvider` 按请求动态生成三类策略：

| 策略 | 判定条件 | 用在 |
|---|---|---|
| `Domain:{code}` | 当前用户可见域包含 `{code}` | 各业务端点组、页面根 |
| `Access:Configure` | 用户 `page_level ≥ 2` | 只服务配置类页面的端点组（如 `/api/shift-schedules`） |
| `PlatformAdmin` | 固定实现，要求 `super-admin` | 平台管理相关端点 |

- `super-admin` 在三类策略内**短路返回成功**，不查授权表——这样新增域不必给超管补授权；
- 结果缓存 30 秒（授权变更后最迟 30 秒生效，可接受）。

**页面等级必须在页面组件入口再判一次**，不能只靠策略。原因：端点组按域划分，而同一域内既有查看类页面也有配置类页面（能耗页与排班页同属钞纸域）。只按域判定的策略拦不住「普通用户直接输入配置页地址」——他会看到一个能打开的页面，只是数据接口 403，体验和安全性都不对。

### 7.4 根路由问题

`/` 现在是能耗仪表板，属于钞纸域。未获钞纸域授权的用户访问 `/` 会 403。因此**登录后的默认跳转不能再写死 `/`**，改为「第一个可见域的首个页面」，见 12.2。

## 8. 数据模型

新增 11 张表，均带 `created_at` / `updated_at`，管理类表另带 `created_by`。

### 8.1 组织与账号

| 表 | 关键字段 | 说明 |
|---|---|---|
| `departments` | `id`, `code`(唯一), `name`, `external_code`, `is_enabled` | `external_code` 对应 LDAP 的 `department` 属性值或 OIDC 的组名 |
| `app_users` | `id`, `user_name`(唯一), `display_name`, `department_id`, `email`, `is_enabled`, `disabled_source`, `security_stamp`, `must_change_password`, `password_hash` | `department_id` 单值可空（外部账号未同步到部门时为 null，此时不可见任何业务域）；`disabled_source` ∈ {`manual`, `directory`}，区分「人停的」与「同步停的」，见 9.5；`security_stamp` 换值即撤销该用户全部已签发会话，见 9.5 |

`departments` **刻意没有 `parent_id`**：已确认部门之间平级、无下级，与 LDAP 侧的组织模型一致。不预留层级字段是有意的——预留但不用，容易被误当成「将来会支持树形」而在权限判定里写进不该有的递归逻辑。若将来真出现层级需求，届时加字段并补迁移，成本低于现在猜一个用不上的结构。

| `domain_pages` | `id`, `page_key`(唯一), `domain_id`, `route`, `title`, `group_title`, `icon`, `accent`, `access_level`, `sort_order`, `is_enabled`, `source`, `is_orphaned` | `access_level` ∈ {1 查看, 2 配置}；`source` ∈ {`code`, `override`}，决定启动对账是否覆盖 |

| 表 | 关键字段 | 说明 |

### 8.5 目录同步待处理队列

| 表 | 关键字段 | 说明 |
|---|---|---|
| `directory_sync_issues` | `id`, `provider`, `issue_type`, `external_code`, `sample_user_name`, `occurrences`, `first_seen_at`, `last_seen_at`, `resolved_at`, `resolved_by` | `issue_type` ∈ {`department-unmatched`, `user-name-conflict`}；部分唯一索引 `(provider, issue_type, external_code) WHERE resolved_at IS NULL` |

为什么单独建表而不是只写审计：审计是「发生过什么」的流水，这里是「现在还剩什么没处理」的待办。管理员需要反复打开一张短列表，且要能标记已处理——用审计表兼做待办，要么查不动，要么只能靠时间窗口猜。

已处理的行**不删除**，只打 `resolved_at`。同一问题再次出现会另起一行（`occurrences` 从 1 起），这样「上个月处理过、这个月又冒出来」在列表里是可见的；如果就地复用旧行，反复出现的问题会被悄悄累加成一个陈旧时间戳。

## 9. 权限点与内置角色

### 9.1 权限点清单

| 编码 | 名称 | 覆盖操作 |
|---|---|---|
| `action.shift.manage` | 排班配置 | 排班导入、增删改、轮转校验触发 |
| `action.user.manage` | 用户管理 | 新建/停用用户、分配角色（部门管理员受范围限制，见 9.3） |
| `action.domain.manage` | 域与页面管理 | 新建域、改页面归属、启停页面 |
| `action.department.manage` | 部门与授权管理 | 新建部门、配置「部门 × 域」矩阵 |
| `action.system.manage` | 平台配置 | 点位配置、点位数据管理、采集服务器、接口联调 |

新增权限点只在出现**新的写操作**时才加，不为读操作建点。

### 9.2 内置角色

| 角色 | code | 页面等级 | 权限点 | 可见域 |
|---|---|---|---|---|
| 超级管理员 | `super-admin` | 99（短路，不查授权） | 全部 | 全部业务域 + 系统域 |
| 部门管理员 | `department-admin` | 2（含配置类页面） | `action.user.manage`（仅本部门）+ `action.shift.manage` | 本部门已授权域 |
| 技术人员 | `technician` | 2（含配置类页面） | `action.shift.manage` | 本部门已授权域 |
| 普通用户 | `viewer` | 1（只看查看类） | 无 | 本部门已授权域 |

部门管理员是技术人员的超集（多一项用户管理），避免出现「看得见排班页却改不了」的尴尬组合。

**部门管理员默认不启用**：角色存在于表内但 `is_enabled = false`，用户管理页不提供该选项。需要时改一个开关即可启用，不影响既有数据。

**超级管理员全局仅一个账号**：不可新增、不可删除、不可停用，更换只能走「移交超管」（6.4）。因此上表中 `super-admin` 的「可见域」列虽然写「全部」，实际是短路结果，不产生任何授权记录。

### 9.3 部门管理员的边界

可以：查看本部门用户、停用/启用、在「普通用户 / 技术人员」之间调整角色、编辑本部门已授权域内的配置类页面。

不可以：

- 授予 `department-admin` 及以上角色（防自我提权链）；
- 修改本部门的域授权（域授权只由超管配置）；
- 跨部门操作。

约束实现方式：`action.user.manage` 的校验装饰器读取「操作者部门」，与被操作用户的部门比对，不一致直接拒绝。**仅靠界面隐藏下拉项不安全**。

**「本部门」= `department_id` 精确相等，不递归**。组织模型没有层级——LDAP 侧同样是一个用户一个部门、部门之间平级，因此不需要树形递归，也不存在「管 A 部门自动管 A 下面的车间」这种情况。这一点在实现上省掉两件事：查询不必带 `path` 或递归 CTE，校验就是一次 `==` 比较。

连带的一条约束：**部门管理员不能修改任何用户的 `department_id`**。跨部门调动属于超管操作，否则部门管理员可以把别部门的人「拉」进本部门再处置。

### 9.4 审计（只记录配置类写操作）

#### 记录范围

| 类别 | 具体操作 | 是否记录 |
|---|---|---|
| 排班配置 | 导入、清空、逐条修改 | 是 |
| 采集配置 | 点位增删改、点位数据增删改、采集服务器增删改 | 是 |
| 权限配置 | 用户增删改、角色分配、部门增删改、域增删改、页面归属/等级/启停变更、部门域授权变更 | 是 |
| 登录 | 登录成功、失败、锁定 | 否 |
| 查询 | 所有 GET 请求、报表查看、导出 | 否 |

判据只有一条：**是否改变了系统配置**。业务数据（采集记录、能耗指标）不在本期范围——它们由采集端自动写入，量级与配置操作不在一个数量级，记录会产生大量噪声。

#### 写入方式

配置类写操作与审计记录**放在同一个数据库事务**里：业务写入成功而审计落库失败时整体回滚。

理由：配置类操作频率极低（人工操作，日均个位数到百位数），回滚代价可接受；反过来"改了但没留痕"会让审计形同虚设。这与"查询日志可丢"的取舍不同。

失败的操作也要记录（`result = 'failed'`），否则连续尝试越权的痕迹会消失。

`actor_user_id` 永远是**员工个人**，不会出现「班组」或「大屏」。只读的设备账号（6.5）不产生审计记录；若将来给它开放写权限，这部分操作就失去追责对象，因此该账号的权限应固定为只读。

#### 保留与查看

- 保留期默认 180 天（已确认采用默认值，无需另设），可按配置调整（`Auth:Audit:RetentionDays`）；过期由后台任务按 `occurred_at` 分批删除，避免大事务。
- 查询界面在「平台管理 → 系统审计」：按时间段、操作人、对象类型、结果筛选，支持导出 CSV。
- 审计日志**只读**：不提供任何修改或删除入口，超管也只能查询。

#### 与权限的关系

`audit_logs` 的查询权限归 `action.system.manage`（平台管理域）。不新增独立权限点——审计页属于平台运维范畴，与现有超管职责一致。若将来要把审计权限单独授予合规岗，再加 `action.audit.read` 即可，表结构不用改。

### 9.5 停用语义与会话撤销

两件事必须分开看，混在一起会出两种相反的事故：

**停用来源（`app_users.disabled_source`）**

| 取值 | 谁写的 | 目录同步怎么处理 |
|---|---|---|
| `manual` | 管理端停用（单个或批量） | **保持停用**，不自动恢复 |
| `directory` | 同步发现目录里禁用或账号已删除 | 目录恢复后自动启用 |
| 空 | 历史数据 / 启用中 | 按 `directory` 处理（保持升级前的行为） |

不分来源会怎样：管理员把某人临时停用（离职流程中、借调、调查期间），一小时后的定时同步发现「目录里这个人还在且启用」，就把它悄悄打开了——没有任何提示，界面上也看不出是谁打开的。

反过来也要能自动恢复：目录里恢复的人如果还得挨个手工启用，同步就失去意义。所以判定的关键是「这次停用是谁做的」，而不是「目录里是什么状态」。

**会话撤销（`app_users.security_stamp`）**

授权只认 Cookie 里的 claims，会话一旦签发就与库脱钩。因此停用与重置密码这两件事原本要等绝对过期（默认 12 小时）才生效，而这正是最需要立刻生效的两个操作。

- 签发时把 `security_stamp` 写进 claims；
- 每个请求在 `OnValidatePrincipal` 里与库比对（30 秒缓存），不一致即拒绝并清 Cookie；
- 停用、启用、重置密码、改密、移交超管都会换戳。

**刻意不换戳的操作**：改角色、改域授权。原因是既定设计——「授权变更下次登录生效，会话内不热切换」。换戳会把用户当场踢下线，与这条设计冲突，也会让「改个角色」变成一次强制重新登录。

**Blazor 电路的边界**：`OnValidatePrincipal` 只在 HTTP 请求上跑。已建立的 Server 电路不会因为换戳而断开，最长活到绝对过期。为此领域服务装饰器在每次写操作前额外回查一次「账号是否仍然启用」，把电路内的写操作也堵住。读页面（已渲染的数据）不做这个检查——数据已经发出去了，拦不住，也没必要。

## 11. 外部对接

**P3（LDAP）与 P4（OIDC）均已落地并完成端到端实测**（2026-11-03）。下面两张表是设计基线，实现细节与实测结论见 13.3。

### 11.1 LDAP / AD（P3）

| 环节 | 做法 |
|---|---|
| 连接 | LDAPS 636；若用 StartTLS 则 389 + 升级 |
| 验证 | 服务账号（只读）bind → 按 `sAMAccountName` 或 `userPrincipalName` 搜到用户 DN → 用该 DN + 用户输入密码二次 bind |
| 唯一键 | `objectGUID`（转 16 进制字符串），回退 `sAMAccountName` |
| 属性 | `displayName` → 姓名；`mail` → 邮箱；`department` → 部门；`userAccountControl` → 启停 |
| 部门回退 | `department` 为空时解析 DN 的 OU 层级，取配置指定层级的名称 |
| 搜索 | 分页结果（AD 默认单页 1000，必须分页否则大目录静默截断） |
| 同步 | 定时**全量**（默认每小时，`SyncIntervalMinutes` 配 0 则只手工触发）；登录时再做一次实时校验，防止已停用账号继续登录 |

**增量同步（`whenChanged`）尚未实现**，当前只有全量分页。几千人以内的目录每小时全量拉一遍没有压力；如果将来对接的目录上万人，再补 `whenChanged` 增量（届时把同步时间戳落库，filter 改成 `(&(objectClass=user)(whenChanged>=...))`）。这一条写在文档里是为了避免「以为有增量、结果每小时扫全表」。

**证书信任**：LDAPS / StartTLS 使用操作系统信任库校验服务器证书，平台**不提供**关闭校验的开关（这是刻意的——关掉校验等于把域账号密码交给任何能劫持 DNS 的人）。内网自签 CA 请把根证书装进操作系统的受信根（Linux：`/usr/local/share/ca-certificates` + `update-ca-certificates`；Windows：受信任的根证书颁发机构），而不是在应用里绕过。

部门匹配策略：`departments.external_code` 与 LDAP 的 `department` 值比对；未匹配到时**不自动建部门**，记入待处理队列由超管确认——自动建部门会让组织树随目录里的脏数据膨胀。

### 11.2 OIDC（P4）

| 环节 | 做法 |
|---|---|
| 流程 | Authorization Code + PKCE；code 换 token 在服务端完成 |
| 唯一键 | `sub`（**不用 email**，邮箱可变；不用 `preferred_username`，可能被回收复用） |
| 属性 | `name` → 姓名；`email` → 邮箱；`groups` 或自定义 claim → 部门 |
| 部门映射 | 配置化：claim 名、取值前缀、映射到 `departments.external_code` 的规则 |
| 首次登录 | JIT 建号，默认角色 `viewer`，部门由 claim 映射；映射不到则建号但不可见任何业务域，记入待处理 |
| 多 IdP | `Authority` / `ClientId` / `Scope` / claim 映射全部配置化，新增一家只加一段配置 |

### 11.3 三条铁律

1. **幂等 upsert，只更新可同步字段**：姓名、邮箱、部门、启停。**绝不覆盖本地已分配的角色**——否则每次目录同步都会把手工配的权限冲掉。
2. **账号保留优先于删除**：目录中消失的账号标记 `is_enabled = false` 并记录 `last_synced_at`，不物理删除，避免历史引用断链。
3. **目录返回 0 条时整轮作废**：读到空列表一律当作「目录不可用或过滤条件写错」，跳过停用阶段并写 `result=failed` 的审计。少了这一条，一次误配的 `SyncFilter` 会在几秒内停用全平台账号。

## 12. 关键流程

### 12.1 登录

```
输入账号密码
  → 本地校验 或 外部 IdP 回调
  → 签发 Cookie
  → 拉取 /api/auth/me（含可见域、页面等级、权限点）
  → 12.2 计算落地页
```

### 12.2 落地页计算

四个分支，必须分开处理——它们的用户诉求完全不同，落到同一个 403 页会让人无从判断该找谁：

```
1. 超级管理员                    → /platform-overview（短路，不看域）
2. 可见域中存在有页面的域         → 该域内 sort_order 最小的页面
3. 可见域全部为空域（有授权无内容）→ /coming-soon（「你所在的部门已获授权，对应板块尚未上线」）
4. 没有任何可见域                 → /no-access（「你的部门尚未被授予任何业务域，请联系管理员」）
```

| 场景 | 用户该做什么 | 页面文案方向 |
|---|---|---|
| 空域（分支 3） | 等待，无需操作 | 说明已授权、板块在建设中，不要出现「无权限」字样 |
| 无域（分支 4） | 找管理员 | 说明缺授权，给出联系方式或管理员姓名 |

超管落地页固定为 `/platform-overview`。
普通用户若钞纸域可见，落地页为钞纸域排序第一的页面，当前是能耗仪表板 `/`。
车间终端的只读会话走分支 2，落地页同样是 `/`——**不需要为它单独写落地逻辑**，这也是"复用同一套授权路径"带来的直接好处。

**这一点必须实现，否则未授权钞纸域的用户一登录就 403，观感等同于系统故障。** 分支 3 尤其容易漏：授了域但页面还没开发出来时，系统看起来和"没授权"一模一样。

### 12.3 域切换

点击顶栏域，三种情形：

| 情形 | 行为 |
|---|---|
| 当前页面属于该域 | 只切换左侧菜单，不跳转（沿用现有逻辑） |
| 不属于该域，且该域有页面 | 跳到该域首个页面 |
| 该域为空（仅超管可见） | 不跳转，左侧渲染空状态与「前往域与页面配置」入口 |

第三种不能跳 `/coming-soon`：那会让超管失去从顶栏回到配置页的路径，空状态直接内联在抽屉里更合理。

### 13.2 P2 实现要点

| 议题 | 结论 |
|---|---|
| 部门管理员看不到平台管理域，如何进用户管理页 | 新增**跨域共享页**：`NavItem` 带 `RequiredPermission` + `IsShared`，共享页「持有权限点即可见」，不参与域授权矩阵。非超管时导航里合成 `shared-admin`（显示名「权限管理」）域承接这类页面；超管照旧在平台管理域看到，不重复渲染。页面闸门同步：共享页按权限点 + 等级判定，其余页仍走域 + 等级。 |
| 部门管理员的边界 | 列表按 `department_id` 精确相等过滤（不递归）；新建账号强制落本部门，请求里指定别部门会被静默改写；可授予角色仅 `viewer` / `technician`（授予 `department-admin` 会形成自我提权链）；调整部门与移交超管只对超管开放。 |
| 超管账号保护 | 不可停用、不可调部门、不可被他人重置密码、不可直接改角色；唯一例外是本人改自己的密码。更换超管只能走「移交超管」：同一事务内先降级再升级，不留「零超管」中间态，移交后当前会话必须重新登录。 |
| 停用与角色变更何时生效 | 一律**下次登录生效**。授权只认 Cookie 里的 claims，会话内不热切换；需要立即阻断时先停用（后续登录被拒），已签发会话最迟在绝对有效期后失效。 |
| 越权尝试是否留痕 | 要留。`Administrator` 类操作在范围校验、提权校验、超管保护三处拒绝时写 `result=failed` 并附中文原因，否则连续尝试越权在审计页上完全不可见。未登录时无法归到人，由端点策略先拦，不落审计。 |
| 部门管理员开关 | `Auth:DepartmentAdmin:Enabled` 默认关闭。打开时启动初始化把内置角色翻到启用，**只朝启用方向生效**——配置改回 `false` 不会回滚人工启用，人工决定优先于默认值。 |
| 审计查询的性能边界 | 分页上限 200 行/页，导出上限 20000 行（人工核对用途，超限请缩时间范围）。保留期清理走后台任务分批删除（每批 500），避免大 DELETE 锁表。 |
| 审计页的时间筛选 | `occurred_at` 是 `timestamptz`，Npgsql 只接受 offset 0 的 `DateTimeOffset`；页面带出的是本地时区（`+08:00`），**必须在服务端 `ToUniversalTime()` 后再拼进 `Where`**，否则整个查询抛异常。 |
| 导航查询的上下文隔离 | 导航由 `MainLayout` 在渲染时加载，与页面自己的 `OnInitializedAsync` 并行发起。两者共用同一个 scoped `DbContext` 会撞「A second operation was started on this context instance」，因此 `NavigationViewService` 自己开 scope 取上下文。**页面里任何与布局并行的查询服务都应遵循这条**。 |

**车间终端必须与 P1 同批上线，不能往后排。** 理由很直接：启用登录之后，那台公用电脑上没有任何人应该"代表全组"登录，如果届时没有白名单，上线当天班组就看不到能耗数据——这不是权限问题，是生产现场直接失去数据来源。它依赖的只是既有排班数据与只读端点，工作量不大，但漏掉的后果很明显。**该机器的地址已确认固定（2026-11-03），此前唯一的阻塞项已解除**：验收时不会出现"一会儿免登录、一会儿要登录"的现象；实施时需把实际地址写入 `Auth:Board:IpWhitelist` 并与现场机位核对一次。

### 13.3 P3 / P4 实现要点

配置全部落在 `Auth:Ldap` 与 `Auth:Oidc` 两节（`Security/Directory/LdapOptions.cs`、`Security/External/OidcOptions.cs`）。启动时 `AuthDataInitializer.ValidateExternalIdentityOptions()` 校验，**配置不完整直接拒绝启动**——外部认证配错的表现是「谁都登不上」，等到运行时才发现就太晚了。

| 议题 | 结论 |
|---|---|
| LDAP 用什么包 | `System.DirectoryServices.Protocols`，不用 `System.DirectoryServices`（后者仅 Windows）。连接一律 `new LdapConnection($"{host}:{port}")` 字符串构造：`LdapDirectoryIdentifier(host, port)` 在本机回环地址上会连不上，排查成本极高。 |
| 明文 LDAP 怎么管 | `TransportSecurity` ∈ {`None`, `Ssl`, `StartTls`}。选 `None` 时**只允许 loopback 主机**（判定用 IP 而非「是否开发环境」——`ASPNETCORE_ENVIRONMENT` 可以被误设）。StartTLS 必须在 bind 之前升级。 |
| 过滤器注入 | 用户名拼进过滤器前做 RFC 4515 转义（`\5c \2a \28 \29 \00`）。不转义时 `(sAMAccountName=*)` 会命中目录里的第一个人，等于任意登录。 |
| 空密码 | 必须在本地挡掉。LDAP 协议里「DN + 空密码」是一次**匿名 bind**，服务器会返回成功。 |
| 目录密码错误怎么报 | 统一「账号或密码不正确。」，不区分「用户不存在」；**本地不累计失败次数**——AD 有自己的锁定策略，两边各锁一次会让「密码错两次」在现场表现成「账号被锁」。 |
| 唯一键缺失 | `UniqueIdAttribute` 取不到时回退登录账号（OpenLDAP 的 `entryUUID`、AD 的 `objectGUID` 都属可能缺失项）。`DisabledFlagAttribute` 缺失或非数字**一律视为启用**，否则首轮同步会把全员停用。 |
| 同名冲突 | 目录里的新人拿到了一个已被本地账号占用的用户名时，**不并号**：记 `user-name-conflict` 待处理项，跳过该人。合并等于把别人的历史数据交给另一个人。 |
| 重新启用 | 目录中重新出现且本地已有绑定 → 走 update 把 `is_enabled` 翻回 true，不新建账号。前提是唯一键稳定，所以 `UniqueIdAttribute` 要选不会变的属性（`objectGUID` / `entryUUID` / `uid`，不要用 `whenChanged` 之类的动态属性）。 |
| 同步周期 | `SyncIntervalMinutes`，默认 60；配 0 表示只在手工触发时同步（联调与演示用）。后台任务启动延迟 30 秒，单轮失败不退出循环。 |
| OIDC 用什么实现 | 复用 `Microsoft.AspNetCore.Authentication.OpenIdConnect`：state / nonce / PKCE / 元数据缓存 / 签名校验由框架实现。每家 IdP 一个 scheme `oidc-{code}`，回调 `/api/auth/oidc/{code}/callback` **必须落在 `/api/auth` 免登录白名单内**，否则 IdP 带 code 回跳时会被当成未登录请求 302 回登录页。 |
| `response_mode` | 框架默认 `form_post`，即 IdP 用自动提交表单把 code POST 回来。**自测时不能假设是 query 回跳**，模拟 IdP 必须实现 form_post，否则永远走不到回调。 |
| 多 IdP 的绑定键 | `provider` 存 `oidc:{code}` 而不是 `oidc`。两家 IdP 的 `sub` 各自独立编号，只用 `oidc` 会让两家的第一个人撞成同一个账号。 |
| 多值部门 claim | `groups` 这类 claim 一次给出全部组，**只取第一个值会把 `staff` 当成部门**。配了 `DepartmentPrefix` 就按前缀挑，挑不到再退回第一个值（让匹配失败进待处理表，而不是静默变成「无部门」）。 |
| 部门映射的统一入口 | LDAP 与 OIDC 共用 `DepartmentCodeResolver`，按 `departments.external_code` 精确匹配；匹配不到一律进 `directory_sync_issues`，**不自动建部门**。 |
| OIDC 建号冲突 | 同名时加 `-{providerCode}` 后缀再试，不并号。 |
| 手工角色 | 两条通道都只刷新姓名/邮箱/部门，**从不写 `user_roles`**。已实测：把域账号改成 `technician` 后再同步 / 再登录，角色保持不变。 |
| 界面 | 用户管理页底部新增「目录同步」区块（仅超管可见）：立即同步、最近同步时间与摘要、待处理表（中文说明 + 「怎么修」提示 + 标记已处理）。 |

### 13.4 外部认证的实测记录（2026-11-03）

| 场景 | 环境 | 结论 |
|---|---|---|
| LDAP 全量同步 | OpenLDAP 容器（明文 389 → 宿主 3389）+ 三个账号（`PAPER1` / `PRINT2` / 不存在的部门） | 三个账号建号成功；两个部门按 `external_code` 正确匹配，第三个进待处理表 |

| 空目录保护 | 删光全部人员后同步 | 返回「目录未返回任何账号，已跳过停用阶段，账号保持原状」，三人全部保持启用，审计记 `result=failed` / `stage=fetch` |
| 口令失败 | 连续 6 次错误密码后正确密码 | 全部提示「账号或密码不正确。」，第 7 次正常登录，本地未累计锁定 |

| 第二家 IdP 仅靠配置 | 第二家用完全不同的 claim 名（`display_name` / `mail` / `upn`）与 `dept:` 前缀 | 只加配置即接入，代码零改动 |

### 13.6 第二轮全量审读（2026-11-03 夜）

这一轮不是查认证，而是通读全部后端代码后找**逻辑层面**的缺口。最重要的一条只有跑起来才会暴露：
定时采集看起来「在工作」（日志有周期、上游有请求），实际上**一条数据都没入库**。

| 编号 | 缺口 | 后果 | 处理 |
|---|---|---|---|
| **D1** | 采集执行通过 `UpsertCollectionPointAsync` 写采集点状态，而这条路径带 `action.system.manage` 权限守卫 | 后台调度器没有操作者 → 每次采集在写库前抛 `ForbiddenAccessException`，**数据永不入库**；同时每 5 秒给审计表写一批失败记录（12 个节点 ≈ 每分钟 144 条）。实测确认：修复前采集记录停在两周前，修复后 12 秒内入库 11 条 | 抽出 `CollectionPointStateSynchronizer`：采集点状态属于**数据面**，用仓储直写、不做权限判定；配置修改仍只走带守卫的入口。调度器与执行服务共用同一实现 |
| D2 | `/api/auth/me` 对没有 `UserId` 的车间只读会话返回 401 | WASM 端据此判为匿名并跳登录页 → 免登录看板在「第二次访问（WASM 缓存命中）」时整页失效，第一次却是好的，极难复现 | `AuthUserDto` 增加 `IsBoardTerminal`；`/me` 对只读会话返回合成身份（`Id = Guid.Empty`，钞纸域 + 等级 1）；WASM 主体补 `board` claim，顶栏仍显示「车间终端 · 只读」且不出现登出 |
| D3 | `/api/collection-data/ingest` 只要求钞纸域 | 任何普通查看者、包括车间只读终端，都能写入任意测量值；这些值直接进报表与能耗计算 | 加 `action.system.manage`。机器采集端接入需要独立凭据（API Key），不能复用人员权限——这是下一步而不是当前 |

**这一节没有改的**（明确记录，避免下次重复讨论）：

- 登录失败不落 `audit_logs`。原因是审计保留 180 天，而限流上限是 20 次/分钟/IP，
  一个针对真实账号的爆破即可在保留期内写入数百万行——用审计表抗拒绝服务是反向的。
  登录失败已进应用日志；若合规要求必须入库，应先做「同一账号失败聚合」而不是逐条写。

### 13.7 管理界面覆盖核对（2026-11-03 深夜）

问题来自「页面能不能满足需求、管理页有没有覆盖文档里的管理功能」。核对方式是**先列文档要求，再逐页跑起来点**，不看代码猜。

| 菜单「点位配置 / 点位数据管理」与页面标题「采集点配置管理 / 后台数据管理」不一致 | 用户点进来会怀疑入错口 | 页面标题统一为菜单名 |
| 页面保存成功后提示立即消失（`LoadAsync` 无条件清空 `_message`） | 管理员看不到「已保存」，会重复点 | 加载方法增加 `clearMessage` 参数，变更后刷新保留提示 |

同批核对确认没问题的：17 个功能页全部能渲染、控制台无错误；页面主色与 `DESIGN_SYSTEM.md` 2.3 表一致；新增管理端点对普通用户一律 403；导航按域/等级/权限点过滤正常。

**仍然没做的**（写在 6.1，属于部署选项而非管理页功能）：`Auth:SharedTerminalMode` 的空闲登出与禁用持久化 Cookie。

### 13.1 与印钞 / 能源排期的关系

两域的页面已排期，但近期开发测试仍集中在钞纸。这个时序对分期有一个明确要求：

**P1 的导航改造必须按「域数量可变」实现，不得对钞纸域做任何硬编码。** 具体要求是：顶栏渲染的是「当前用户可见域列表」，不是三个固定项；域内分组与页面全部来自 `domain_pages`；域策略由 `IAuthorizationPolicyProvider` 动态生成。做到这三点后，印钞/能源页面开发时只需在代码里声明 `DomainCode`、部署后自动入库、再去矩阵勾选部门，**不需要再动导航代码**。

反过来说，如果 P1 图省事写成「顶栏固定渲染钞纸 + 平台管理」，等印钞页面出来就得改一次导航，届时还要迁就已经上线运行的授权数据，成本比现在做对要高。

由于近期只测钞纸，P1 交付验收可以只验钞纸域：另建一个临时测试域（不挂页面）验证「空域对普通用户隐藏、对超管可见」与「域增删不改代码」两条即可，不必等真实页面。

## 14. 风险与决策记录

| 风险 | 影响 | 应对 |
|---|---|---|
| 启用登录即锁死 | 无人能进 | 超管种子 + 配置缺失时拒绝启动（6.4） |
| 页面纯数据库配置导致新页面静默不可见 | 上线后功能"消失"，无报错 | 启动对账 + `is_orphaned` 标记（4.1） |
| 服务端直调领域服务绕过端点鉴权 | 权限形同虚设 | 领域服务入口装饰器（7.2） |
| 未授权用户访问 `/` 直接 403 | 观感等同故障 | 动态落地页四分支（12.2） |
| 空域被普通用户看到 | 点进空白页，被当成"权限没配好" | 默认对非超管隐藏；超管可见并带「未上线」标记（5.2） |
| 页面等级误配（把配置页调成查看类） | 越权可见，且不会报错 | 改档二次确认 + 审计留痕 + 支持一键恢复代码默认值（4 节） |
| 审计表随配置操作增长 | 查询变慢、磁盘占用 | 默认 180 天保留 + `(occurred_at)` 索引 + 分批清理（9.4） |
| 域数量增长后矩阵变宽 | 配置界面难用 | 矩阵支持横向滚动 + 按域分组筛选；域超过 12 个时改为「按部门编辑」抽屉 |
| 单超管不可用（休假、离职） | 期间无人能改域授权与角色 | 预留 `department-admin` 开关可临时启用；移交超管走单独流程（6.4），不放宽唯一性 |
| 白名单写成网段 | 整个网段的人都能读到全部班组数据，且不会报错 | 生产只允许单机 `/32`；启动时对 `/0`–`/24` 输出告警（6.6） |
| 车间机器 IP 漂移（DHCP 重分） | 轻则终端退回登录页，重则别人的笔记本开机即得只读会话 | **地址已确认固定（2026-11-03）**，风险已消除；仍保留会话绑定签发 IP + 固定 12 小时不滑动，作为地址万一变化的兜底（6.6） |
| 部署到反向代理后 `X-Forwarded-For` 被伪造 | 任何人带上伪造头即可获得只读会话 | 只信任已知代理；当前直连 Kestrel 无此风险；加代理必须同批配置 `ForwardedHeaders`（6.6） |
| 排班未导入/过期时"猜"班组 | 现场看到错误班组的数据，且无人察觉 | 默认值必须走严格解析 `TryResolveOnDutyTeam`；不命中就不给默认值，改由用户手选（6.6） |
| LDAP 明文传输被误配到生产 | 域账号密码以明文过网 | 选 `TransportSecurity=None` 时只放行 loopback 主机，非回环地址直接拒绝启动（13.3） |
| 同步过滤器写错导致目录返回 0 条 | 一次同步停用全平台账号，现场全员登录失败 | 读到 0 条整轮作废，跳过停用阶段并写 `failed` 审计（11.3） |
| 用户名未转义拼进 LDAP 过滤器 | 输入 `*` 即命中目录第一人，等于任意登录 | 一律 RFC 4515 转义后再拼接（13.3） |
| LDAP 口径的空密码被当成匿名 bind 成功 | 空密码也能登录 | 空密码在本地拦截，不下发到目录（13.3） |
| 目录同名账号被合并 | 新人的数据挂到老账号名下，历史记录串号 | 记 `user-name-conflict` 并跳过，不自动并号（13.3） |
| OIDC 两家 IdP 的 `sub` 撞号 | 两家的「第一个人」变成同一个平台账号 | `provider` 存 `oidc:{code}`，绑定键带提供方编码（13.3） |
| 多值 `groups` 取第一个值 | `staff` 被当成部门，用户看不到本该有的数据 | 配了 `DepartmentPrefix` 就按前缀挑；挑不到进待处理表（13.3） |
| 目录同步自动恢复「人工停用」 | 被停用的人一小时后重新能登录，且无人察觉 | `disabled_source` 区分来源，只恢复 `directory` 来源（9.5） |
| 重新部署丢数据保护密钥 | 全员同时掉线，现象像网络故障 | 密钥环落盘 + 固定应用名，启动日志打印路径（13.5 A2） |
| 多实例重复跑后台任务 | 唯一索引冲突、审计翻倍 | PostgreSQL 咨询锁互斥（13.5 A3） |
| 密码喷洒 / PBKDF2 计算型 DoS | 站点被拖慢，且不需要知道任何账号 | 认证端点按 IP 限流 20 次/分钟（13.5 B1） |
| 反向代理后客户端 IP 失真 | 白名单失效或全站共用一个限流桶 | 显式配置受信代理才还原转发头（13.5 B3'） |
| 停用/重置密码后旧会话仍有效 | 被停用的人还能继续用 12 小时 | `security_stamp` 换戳撤销 + 装饰器回查启用状态（13.5 B5） |

### 14.1 已确认决策

以下各项均已确认，不再是待定项：

| # | 问题 | 结论 | 对设计的影响 |
|---|---|---|---|
| 1 | 部门是否有下级、部门管理员的「本部门」如何界定 | **无下级，按 `department_id` 精确匹配** | 去掉递归查询；部门管理员不得改他人 `department_id`（9.3） |
| 2 | 印钞 / 能源域页面是否已排期 | **已排期，但近期开发测试仍以钞纸为主** | P1 导航必须按域数量可变实现，禁止硬编码钞纸；验收可用临时空域替代（13.1） |
| 3 | 超管数量 | **仅 1 个** | 唯一性做成硬约束：无新增入口、只能移交、启动自检数量必须为 1（6.4） |
| 4 | 审计保留期 | **采用默认 180 天** | 不再需要额外配置，`Auth:Audit:RetentionDays` 保持默认值即可（9.4） |
| 5 | 班组与员工 / 部门的关系 | **两个独立维度，班组不作授权单位** | 授权表禁止引用 `team_code`；不为班组设共享账号，多人各自登录看同一份班组数据；本期不做班组级数据过滤；`external_identities` 预留 `employee_no`（3.5、6.5） |
| 6 | 车间公用电脑（3–5 人共用、只看数据）如何免登录 | **IP 白名单 → 签发只读会话** | 单机 `/32` + 固定 IP；claims = 钞纸域 + 等级 1，页面自动收窄为「数据指标」下的 4 个查看类页；不新增 `/board` 路由与专属端点（6.6） |
| 7 | 车间共有几台电脑 | **1 台，所有班组共用** | 白名单只需一条 `/32`；不需要按班组分机位，也不需要管理多份凭据（6.6） |
| 8 | 车间终端是否要深色大屏样式 | **否，沿用当前设计风格** | 复用现有浅色布局与七色色板，不新增深色主题；将来若要做，须先在 `docs/DESIGN_SYSTEM.md` 登记（1.2、6.6） |
| 9 | 车间那台机器的 IP 是否已固定 | **已固定（2026-11-03 现场确认）** | 白名单可按单机 `/32` 落地，`Auth:Board` 无需额外兼容逻辑；实施时把实际地址登记进部署清单并核对白名单（6.6、13） |

至此设计无遗留待定项。实施阶段如遇新问题，追加到本表而不是散落在各节。
